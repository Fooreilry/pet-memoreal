# Регистрация и доступ

Адреса не содержат языка. Автоматический выбор по стране и переключатель описаны в [локализации](localization.md).

## Пользовательский сценарий

1. Откройте `http://127.0.0.1:3000/register`.
2. Введите имя (1–80 символов), email и пароль (8–128 символов), повторите пароль.
3. Откройте письмо в [локальном Mailpit](http://127.0.0.1:8025) и перейдите по ссылке. Подтверждение действует 1 час и не выполняет автоматический вход.
4. Войдите на `/login`. Откроется отдельная страница `/account`: личные данные, ваши места памяти и выход из аккаунта внизу. Сессия сохраняется после перезагрузки.
5. `/verify-email` запрашивает новое подтверждение; `/forgot-password` отправляет ссылку восстановления, `/reset-password` принимает новый пароль из письма.

Локальные письма остаются в Mailpit и не доставляются во внешние ящики. После входа доступно [создание мемориалов](memorial-creation.md). Все страницы и письма имеют RU/EN варианты; язык письма соответствует форме запроса.

## Личный кабинет

Кабинет использует собственную компоновку без регистрационной карточки и рекламного блока. Вверху оставлен заголовок «Мой кабинет» без вступительных подписей; в шапке доступны главная, сад и переключение языка. Логотип — росток без рамки и название PetMemoreal без точки. Круглый аватар с инициалами сопровождает имя, необязательную фамилию и подтверждённый email. «Изменить» открывает форму: имя обязательно, оба поля ограничены 80 символами; пробелы по краям удаляются на клиенте и сервере. Ошибка сохранения оставляет введённый текст. Email здесь не меняется.

Фамилия хранится в `auth_user.surname` (миграция `0003_closed_alex_wilder.sql`). Старые записи получают пустую строку; существующее имя сохраняется без автоматического разделения. Обновление проходит через `/api/auth/update-user` Better Auth с проверкой сессии и origin. `/api/me` возвращает фамилию только текущему пользователю.

Ниже расположены карточки собственных мемориалов: имя питомца, годы жизни, сад, номер места и начало истории. Ссылка «Перейти к месту» открывает конкретный мемориал на карте. Кнопки создания в кабинете нет; пустой список предлагает выбрать место в саду. Ошибка загрузки имеет отдельное состояние с повтором запроса. Красная кнопка выхода находится после списка без дополнительных подписей; успешное завершение сессии открывает гостевой лендинг текущего языка. При неудаче пользователь остаётся в кабинете, сессия сохраняется и доступна повторная попытка.

Главная в `/` показывает информационный лендинг только гостям. Middleware `landing` использует результат общей проверки сессии при SSR и клиентском переходе: авторизованный пользователь сразу попадает в обзор четырёх садов текущего языка. Лендинг не успевает появиться в серверном HTML для пользователя с сессией. Во время гидрации гостевой страницы повторный запрос не выполняется. После выхода или истечения сессии лендинг снова доступен. При отказе сервиса открывается лендинг с уведомлением, см. раздел «Недоступность сервисов».

Лендинг сохраняет статическую компоновку без встроенных действий: все ответы FAQ видны сразу, карточки садов информационные. Кнопки создания ведут на `/register`, вход и прогулка — на `/login`; prefetch этих ссылок отключён. Предварительная генерация главной отключена, её ответы и перенаправления имеют `private, no-store`, чтобы учитывать реальные cookie при каждом переходе.

Middleware `guest` на `/login` и `/register` проверяет подтверждённую сессию через `/api/me`. Гостю показывается форма; пользователь с действующей сессией перенаправляется в кабинет текущего языка. Если передан разрешённый `redirect` в сад или форму создания, используется он; внешние адреса не принимаются. Проверка работает при SSR и клиентском переходе. Ошибка проверки, отличная от 401, возвращает 503. Страницы форм и ответы перенаправления имеют `private, no-store`, чтобы смена или истечение сессии учитывались при следующем переходе. Выход доступен в кабинете и меню садов.

На странице садов `GardenHeader.vue` сохраняется над обзором и выбранной территорией. Иконка аккаунта открывает меню по наведению, касанию или клавиатуре: «Профиль» ведёт в `/account`, «Выйти» завершает сессию и открывает гостевой лендинг текущего языка. Гостю доступны вход и регистрация. Меню использует ARIA-роли, стрелки, Home/End и Escape; наведение сохраняет фокус на карте. При ошибке выхода сессия, выбранный сад и меню аккаунта сохраняются для повторной попытки. Успешный выход очищает кеши Nuxt; сохранённые мемориалы остаются в БД и доступны при повторном открытии публичной карты. SSR проверяет сессию через защищённый `/api/me`, чтобы чтения страницы не расходовали общий лимит публичного auth endpoint. В payload передаётся только признак подтверждённой сессии; HTML `/gardens` имеет `private, no-store`.

## Запуск и настройки

```powershell
docker compose up -d postgres mailpit
corepack pnpm db:migrate
corepack pnpm dev
```

Для собранного сервера: `node --env-file=.env .output/server/index.mjs`. Nuxt dev загружает `.env` автоматически. Используйте адрес из `BETTER_AUTH_URL`, включая хост и порт.

Локальный dev-сервер закреплён за `127.0.0.1:3000` в `nuxt.config.ts`. Переход на страницу через `localhost` или IPv6 loopback с тем же портом перенаправляется на адрес из `BETTER_AUTH_URL`, сохраняя путь и параметры. Это предотвращает отказ регистрации из-за несовпадения `callbackURL` и доверенного origin. API не перенаправляются; проверки origin для авторизации и создания мемориалов остаются строгими. Внешние домены эта логика не затрагивает.

Локальные настройки хранятся в игнорируемом `.env`; облачные задаются в Vercel. Полная инструкция — [Vercel + Neon + Resend](vercel-deployment.md).

| Переменная | Назначение |
| --- | --- |
| `BETTER_AUTH_URL` | Полный origin приложения, локально `http://127.0.0.1:3000`, вне localhost только HTTPS |
| `BETTER_AUTH_SECRET` | Случайный секрет минимум 32 символа; уже создан локально |
| `SMTP_HOST`, `SMTP_PORT` | Локально `127.0.0.1` и `1025` (либо порт Mailpit из Compose) |
| `SMTP_SECURE` | `true` для SMTP с TLS сразу; локально `false` |
| `SMTP_FROM` | Email отправителя; локально `noreply@petmemoreal.test` |
| `SMTP_USER`, `SMTP_PASSWORD` | Задаются вместе, если почтовый сервер требует аутентификацию |

При старте сервер проверяет обязательные настройки авторизации и базы. При ошибке публичный лендинг остаётся доступен; последующие запросы повторяют инициализацию. Сборка не требует секретов. Для реальной доставки нужно указать внешний SMTP и подтверждённый адрес отправителя.

## Устройство и границы доступа

- `server/utils/auth.ts`: Better Auth с Drizzle adapter, серверная валидация имени, отправка писем и лимиты запросов.
- `server/api/auth/[...all].ts`: обработчик Better Auth. Локально IP берётся из сокета; при `VERCEL=1` — из ingress-заголовка `x-vercel-forwarded-for` (резервный — `x-forwarded-for`). Входящий `x-auth-client-ip` всегда заменяется сервером. Заголовки других прокси вне Vercel не принимаются.
- `auth_user`, `auth_account`, `auth_session`, `auth_verification`: таблицы из миграции `0001_gigantic_switch.sql`. Пароли хеширует Better Auth.
- `/api/me` и middleware `auth` разрешают доступ только с сессией подтверждённого пользователя. API возвращает только данные текущего пользователя. Ответы кабинета и авторизации не кешируются.
- HttpOnly cookie, SameSite и проверка origin обеспечиваются Better Auth; HTTPS включает защищённые cookies. Сессия действует 7 дней, обновляется через 24 часа. Смена пароля отзывает все сессии; токен сброса одноразовый.
- Публичная регистрация всегда создаёт роль `user`. Разрешены `user`, `manager`, `developer`, `admin`; общий контракт и матрица прав описаны в `shared/roles.ts`, допустимые значения ограничены в БД. Роль нельзя назначить через регистрацию или изменение профиля; `/api/me` возвращает текущую роль из БД и вычисленные права. Админка доступна через вкладку профиля. Подробнее: [роли и администрирование](roles-and-administration.md).
- Ограничение четырёх ролей добавлено миграцией `0008_role_permissions.sql`. Для существующей базы примените `db:migrate`; облачная база обновляется отдельной командой из инструкции по деплою. Миграция не назначает администратора и не меняет существующие роли. Первый подтверждённый администратор создаётся через `db:seed` или `db:admin` из игнорируемого `.env` (`ADMIN_EMAIL`, `ADMIN_PASSWORD`). Повторное заполнение не сбрасывает его пароль.
- Регистрация существующего адреса, запрос подтверждения и восстановление не раскрывают наличие аккаунта в ответе. Неуспешный вход возвращает общую ошибку учётных данных.
- Лимиты на IP и путь за минуту: 10 регистраций/писем подтверждения/восстановления, 30 входов, 100 для остальных путей. Общие счётчики PostgreSQL хранятся в `auth_rate_limit` (миграция `0004_tricky_scarlet_spider.sql`). Custom storage обновляет строку атомарно, включая параллельные запросы из нескольких функций. Неактивные ключи старше часа удаляются при следующих запросах. Недоступность хранилища не отключает защиту.

## Недоступность сервисов

При отказе PostgreSQL или проверки сессии открывается лендинг с сообщением «Сад временно недоступен. Сейчас не удаётся подключиться к саду. Пожалуйста, попробуйте немного позже». Уведомление доступно при первом открытии и без JavaScript; его можно закрыть. Сессия не удаляется: после восстановления сервиса кнопки снова ведут на нужную страницу.

Глобальное middleware проверяет `/api/me` перед переходами. API выполняет лёгкую проверку доступности таблицы авторизации даже для гостя, объединяет параллельные проверки и кеширует только успешную готовность на две секунды. Cookies и данные сессии не кешируются этой проверкой. Ошибки сервиса дают безопасный 503, отсутствие подтверждённой сессии — обычный 401. Ошибки отправки отдельной формы сохраняют её черновик.

## Проверки

```powershell
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test:unit
corepack pnpm build
corepack pnpm test:e2e
corepack pnpm exec playwright test --config=playwright.outage.config.ts
corepack pnpm test:vercel
```

Playwright запускает отдельный production-сервер на порту 4173. Требуются PostgreSQL, Mailpit и пользователь БД с правом `CREATEDB` (локальный пользователь Compose подходит). Перед тестами создаётся уникальная `petmemoreal_e2e_*` база с миграциями, после тестов удаляется только она. Основная база и существующие письма не очищаются. В CI используются отдельные сервисы с тестовыми настройками.

Сценарии проверяют обе локали и размеры экранов: валидацию, подтверждение и повторное письмо, запрет входа до подтверждения, сохранение сессии, выход, восстановление, отзыв прежней сессии, повторное использование токена, ошибки сети, запрет API без входа и попытки подменить роль/origin.

`landing-auth.spec.ts` проверяет серверные и клиентские перенаправления, отсутствие лендинга для обеих ролей и возврат гостевой страницы после выхода или отзыва сессии. `roles.spec.ts` проверяет ограничения БД и запрет самоназначения роли. Тестовые входы используют `helpers/sign-in.ts`: при 429 ожидают `X-Retry-After` и повторяются один раз. Настройки ограничения запросов приложения сохраняются.

`test:vercel` запускает отдельный сервер на порту 4175: URL-подключение к временной БД, health endpoint, доверенные IP и конкурентные лимиты. Реальные Neon и Resend в локальных тестах не используются.
