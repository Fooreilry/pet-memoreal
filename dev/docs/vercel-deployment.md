# Демо на Vercel + Neon + Resend

## Что будет работать

Язык определяется по стране через Vercel: Россия — русский, остальные страны — английский. URL не содержит `/ru` или `/en`; ручной выбор сохраняется. Дополнительные переменные не нужны, подробности — в [локализации](localization.md).

Nuxt SSR и API работают в Node.js-функциях Vercel, пользователи и мемориалы сохраняются в Neon PostgreSQL. Главная в `/` проверяет сессию: гостю показывает информационный лендинг, авторизованному пользователю сразу открывает сады. Предварительная генерация главной отключена; её ответы и перенаправления не кешируются. Вход и регистрация также проверяют сессию динамически и перенаправляют авторизованного пользователя в кабинет. Better Auth отправляет подтверждения почты и восстановление пароля через SMTP Resend. PixiJS работает в браузере. Docker нужен только для локальной разработки; загрузка фотографий пока не реализована и внешнее S3-хранилище для этого демо не требуется.

Для демо без собственного почтового домена подготовлена отдельная [инструкция Gmail SMTP](gmail-smtp.md). При её использовании SMTP-переменные Resend в этой инструкции заменяются значениями Gmail; шаги Vercel и Neon сохраняются.

Код подготовлен, но публикация требует ваших аккаунтов и значений настроек. Ключи и подключения не размещайте в исходниках или сообщениях чата. Файл `.env.example` не используется.

## 1. Что уже есть и откуда взять домен

- Node.js **24.x**, Corepack и pnpm **12.6.0** из `package.json`.
- Репозиторий проекта в GitHub, аккаунты Neon и Resend уже есть. База Neon подключена, миграции и seed применены; при смене базы повторите шаги ниже.
- Нужен аккаунт Vercel с доступом к репозиторию GitHub. Основной способ публикации в этой инструкции — импорт репозитория через кабинет Vercel.
- Локальный проект остаётся нужен для административных команд миграций и проверки настроек.

У сайта и отправителя писем разные адреса:

| Задача | Как получить адрес |
| --- | --- |
| Открывать сайт | Vercel выдаёт адрес вида `your-demo.vercel.app`; покупать домен сайта для демо не требуется |
| Отправлять письма любым пользователям | Нужен собственный домен с управлением DNS, подтверждённый в Resend |
| Проверить почту только на себе | Временно используйте `onboarding@resend.dev`; письма разрешены только на email владельца аккаунта Resend |

Собственный домен регистрируется за плату у регистратора или через раздел Domains в Vercel. Выберите свободное имя и проверьте стоимость регистрации и ежегодного продления. Например, владея `example.com`, можно настроить почтовый поддомен `mail.example.com` и отправителя `noreply@mail.example.com`. Поддомен не покупается отдельно. Примеры здесь не являются доступными для регистрации или уже принадлежащими вам доменами. Адрес `*.vercel.app` не подходит для подтверждения собственного почтового домена в Resend: у вас нет управления его DNS.

Для первого личного теста можно обойтись без покупки домена; для демо с регистрацией других людей потребуется подтверждённый отправитель. Ограничение `resend.dev` описано в [Resend](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain), получение адреса сайта и покупка домена — в [Vercel](https://vercel.com/docs/domains/working-with-domains).

Vercel Hobby допускает только личное некоммерческое использование. При переходе к коммерческому использованию проверьте [Fair Use](https://vercel.com/docs/limits/fair-use-guidelines) и тариф. Квоты почты и базы смотрите в кабинетах провайдеров; наличие бесплатного тарифа не гарантирует непрерывную доступность.

## 2. Проверить подключения Neon

1. Используйте уже подготовленный проект Neon для демо. При создании другого проекта повторите миграции и seed. Локальная база из Docker остаётся отдельной.
2. Выберите регион Frankfurt / `eu-central-1`, чтобы база находилась рядом с функциями Vercel. В `vercel.json` выбран `fra1`; если нужен другой регион, измените его и регион базы согласованно.
3. В **Connect** выберите одну ветку, базу и роль для демо.
4. С включённым **Connection pooling** скопируйте строку подключения целиком — это `DATABASE_URL`. В hostname будет `-pooler`.
5. Выключите pooling и скопируйте строку той же базы — это `DIRECT_URL` для миграций. В hostname не должно быть `-pooler`.

Сохраните параметры TLS из строки Neon, обычно `sslmode=require&channel_binding=require`. Приложение проверяет сертификат сервера; режимы без проверки и `sslmode=disable` для внешней базы запрещены. Драйверы `pg` и Drizzle сохраняются, включая транзакции и блокировку места при создании мемориала.

При ручной настройке нужны именно `DATABASE_URL` и `DIRECT_URL`. Если интеграция Neon создала `DATABASE_URL_UNPOOLED`, её значение используйте как `DIRECT_URL` в локальном файле настроек демо.

## 3. Подготовить Resend

### Для регистрации других пользователей

1. Добавьте домен отправителя в Resend, например отдельный почтовый поддомен вашего домена.
2. Добавьте DNS-записи, которые показывает Resend, и дождитесь статуса **Verified**. Значения SPF/DKIM берите из своего кабинета.
3. В **API Keys → Create API Key** создайте ключ, например `PetMemoreal demo`, с разрешением **Sending access** и ограничением на выбранный домен. Сохраните значение сразу после создания.
4. Выберите адрес отправителя на подтверждённом домене, например `noreply@mail.your-domain.example`, заменив домен на настоящий.

Настройки SMTP:

| Переменная | Значение |
| --- | --- |
| `SMTP_HOST` | `smtp.resend.com` |
| `SMTP_PORT` | `465` |
| `SMTP_SECURE` | `true` |
| `SMTP_USER` | `resend` |
| `SMTP_PASSWORD` | API key Resend |
| `SMTP_FROM` | Ваш адрес отправителя |

В коде отправка письма ожидается до завершения запроса. Альтернатива — порт `587` с `SMTP_SECURE=false`; для внешнего SMTP тогда обязательно используется STARTTLS. Порт `25` на Vercel не используйте. Локальный Mailpit продолжает работать с прежней конфигурацией.

### Для личной проверки без своего домена

Создайте API key с **Sending access** без ограничения на ещё не подтверждённый собственный домен. SMTP-параметры те же, но `SMTP_FROM=onboarding@resend.dev`. При регистрации укажите email, связанный с вашим аккаунтом Resend. Другие адреса не получат письма: регистрация и восстановление доступа для аудитории демо в этом режиме не готовы. Эта возможность не отменяет обязательное подтверждение почты в приложении.

API key в этом проекте используется как `SMTP_PASSWORD`; отдельная переменная `RESEND_API_KEY` не читается. Добавьте SMTP-переменные в Vercel (шаг 5) и локальный `.env.vercel` (шаг 6). Не помещайте ключ в GitHub или клиентский код.

## 4. Импортировать проект из GitHub в Vercel

1. В Vercel откройте **Add New → Project**.
2. Подключите GitHub и разрешите доступ к нужному репозиторию. Если репозиторий не виден, проверьте доступ Vercel GitHub App к нему.
3. Выберите репозиторий и нажмите **Import**. Убедитесь, что выбранная ветка содержит подготовленные `vercel.json`, `nuxt.config.ts`, `package.json` и `pnpm-lock.yaml`.
4. Проверьте настройки ниже и добавьте переменную `ENABLE_EXPERIMENTAL_COREPACK=1` перед первой сборкой.
5. Нажмите **Deploy**. Первый технический деплой создаёт проект и его адрес. Сборка не требует подключения к базе или SMTP, но страницы с авторизацией и API до выполнения раздела 5 могут возвращать ошибку отсутствующей конфигурации.
6. В созданном проекте откройте **Settings → Domains** и скопируйте постоянный production-адрес. Используйте его в `BETTER_AUTH_URL` на следующем шаге. Настройки можно заполнить сразу при импорте, если точный постоянный адрес уже известен; после первого деплоя всё равно проверьте совпадение.

Официальный процесс: [импорт из кабинета Vercel](https://vercel.com/docs/getting-started-with-vercel#deploy-from-the-dashboard), [интеграция с GitHub](https://vercel.com/docs/git/vercel-for-github).

В настройках проекта проверьте:

| Настройка | Значение |
| --- | --- |
| Framework Preset | Nuxt.js |
| Node.js | 24.x |
| Root Directory | Корень репозитория |
| Install Command | `corepack pnpm install --frozen-lockfile` |
| Build Command | `corepack pnpm build:vercel` |
| Output Directory | Оставить стандартное для Nuxt |

Команды уже указаны в `vercel.json`. Сборка использует Nitro preset `vercel`, создаёт `.vercel/output`, функции работают в Node.js с максимальной длительностью 30 секунд. Обычный `corepack pnpm build` остаётся сборкой Node-сервера для локальных проверок.

Используйте именно адрес из **Settings → Domains**, например `https://your-demo.vercel.app`, а не адрес отдельной сборки. Собственный домен для сайта можно подключить позднее; при смене адреса обновите `BETTER_AUTH_URL` и выполните новый деплой.

## 5. Добавить переменные Vercel

В **Settings → Environment Variables** добавьте значения для окружения **Production**. Здесь Production означает опубликованное демо.

| Переменная | Что задать |
| --- | --- |
| `ENABLE_EXPERIMENTAL_COREPACK` | `1`, чтобы использовать закреплённый pnpm |
| `DATABASE_URL` | Pooled-строка Neon из шага 2 |
| `PG_POOL_MAX` | `3`; необязательно, это значение по умолчанию на Vercel |
| `BETTER_AUTH_URL` | Постоянный HTTPS origin демо, без пути, query или hash |
| `BETTER_AUTH_SECRET` | Новый случайный секрет, минимум 32 символа |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` | Значения из шага 3 |
| `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | Учётные данные и отправитель Resend |

Секрет можно создать локально:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Сохраните его в Vercel. Не меняйте при каждом обновлении: он используется авторизацией. Вручную задавать `VERCEL`, `VERCEL_URL` и IP-заголовки не нужно — это метаданные платформы. Переменные `POSTGRES_*` и `S3_*` из локального Compose на Vercel не требуются. Секреты не должны иметь префикс `NUXT_PUBLIC_`.

`DIRECT_URL` нужен только для административных команд и не требуется работающему приложению. Храните его в локальном `.env.vercel`, как описано далее.

## 6. Проверить схему и настройки перед запуском

Откройте локальный игнорируемый `.env.vercel`. В этом рабочем каталоге он уже содержит оба URL Neon и `PG_POOL_MAX`. Добавьте настройки авторизации и SMTP из шага 5, совпадающие со значениями Vercel. При работе с новым клоном создайте этот файл локально и заполните его из кабинетов сервисов: GitHub его не содержит.

Убедитесь, что в файле есть `DATABASE_URL` и `DIRECT_URL` **одной демобазы**. Локальный `.env` не меняйте. Не задавайте эти URL в переменных текущего PowerShell-сеанса: переменные процесса имеют приоритет над env-файлами Node.js. Содержимое файла в терминал или чат выводить не нужно.

Затем:

```powershell
corepack pnpm db:migrate:demo
corepack pnpm db:seed:demo
corepack pnpm deploy:check
```

- `db:migrate:demo` проверяет, что pooled и direct URL ведут в одну базу, и применяет Drizzle-миграции через `DIRECT_URL`, включая таблицу общих ограничений `auth_rate_limit` из `0004_tricky_scarlet_spider.sql`.
- `db:seed:demo` повторяемо добавляет записи общего сада и четырёх садов карты. Пользователей и личные истории команда не создаёт; примеры на карте встроены в интерфейс.
- `deploy:check` проверяет подключение приложения через `DATABASE_URL`, необходимые таблицы/столбцы, четыре сада, соединение и авторизацию SMTP. Письма не отправляются. Проверка не подтверждает доставку писем или DNS-верификацию отправителя — это проверяется после публикации.

Команды `:demo` требуют `.env.vercel` и оба URL; команды не переходят к локальной базе при отсутствии URL. `.env*` исключены из Git и загрузки через Vercel CLI. Уже выполненные миграции повторно не применяются, seed можно повторять.

Миграции не запускаются при сборке или первом HTTP-запросе. Их применяйте отдельным шагом, чтобы параллельные деплои не меняли схему одновременно.

## 7. Опубликовать демо

После сохранения Production-переменных и успешной проверки откройте **Vercel → проект → Deployments**, выберите production-деплой и выполните **Redeploy**. Изменение переменных само по себе не обновляет уже работающий деплой.

Vercel собирает код из GitHub; локальные изменения в эту публикацию не попадают, пока владелец репозитория не разместит их в выбранной ветке. Автоматическая отправка изменений из этого рабочего каталога не выполняется. Проверьте **Production Branch** в настройках Git проекта: обновления этой ветки запускают production-деплой. GitHub Actions проверяет код отдельно; текущий workflow не является автоматическим условием ожидания для Vercel-деплоя.

Открывайте постоянный домен из `BETTER_AUTH_URL`. Уникальный URL конкретного деплоя не является дополнительным разрешённым origin авторизации.

## 8. Проверить опубликованное приложение

```powershell
$demoOrigin = 'https://your-demo.vercel.app'
Invoke-RestMethod "$demoOrigin/api/health"
```

Ожидается `status: ok`. Endpoint проверяет базу и схему, не возвращает параметры подключения и не проверяет отправку почты. При проблеме с базой возвращает HTTP 503 с `status: unavailable`.

Проверьте вручную:

1. `/`, переходы между садами, работу карты на телефоне.
2. Регистрацию на реальный адрес, получение письма, открытие ссылки на правильном домене и вход.
3. Сохранение имени/фамилии в кабинете после обновления страницы.
4. Создание мемориала через свободное место в саду и сохранение после обновления.
5. Открытие ссылки на мемориал в приватном окне без входа.
6. Выход, повторный вход и восстановление пароля через письмо.

Если Vercel Deployment Protection требует вход для посетителей, настройте доступ для аудитории демо в кабинете Vercel. Это отдельная настройка платформы.

## 9. Обновления и отдельные preview

Для обычного обновления выполните локальные проверки, при наличии новой миграции примените её через `db:migrate:demo`, затем владелец репозитория публикует код в Production Branch. Vercel запускает деплой автоматически; после него выполните smoke-проверку. При изменении только переменных используйте **Redeploy**. Схемные изменения делайте совместимыми с ещё работающей версией. Откат кода в Vercel не откатывает миграции или данные PostgreSQL; перед рискованными изменениями сохраняйте экспорт/резервную копию.

Для первого демо используйте одно окружение Production с постоянным адресом. Не копируйте его секреты и базу в случайные preview-деплои. Для отдельного тестового размещения создайте другой проект Vercel, отдельную ветку/базу Neon, свой постоянный адрес и секреты. Текущая конфигурация намеренно не доверяет всем `*.vercel.app`.

GitHub-интеграция может автоматически создавать Preview для других веток и pull request. Пока для них не заданы отдельные база, SMTP и постоянный доверенный адрес, такие деплои не являются рабочими стендами; их можно отключить в настройках проекта. Production-переменные не следует переносить в Preview ради устранения ошибок конфигурации.

### CLI как дополнительный способ

При публикации из репозитория использовать CLI Vercel необязательно. Если потребуется выгрузить настройки локально, выполните `corepack pnpm dlx vercel login`, затем `corepack pnpm dlx vercel link` и выберите **существующий** импортированный проект. Проверьте его через `corepack pnpm dlx vercel project inspect`. Команда `corepack pnpm dlx vercel env pull .env.vercel --environment=production` выгружает переменные, но Secret/Sensitive значения могут быть недоступны: их потребуется заполнить локально. После выгрузки проверьте `DIRECT_URL` и сохранность нужных значений.

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| Не устанавливается pnpm | Node 24, `ENABLE_EXPERIMENTAL_COREPACK=1`, закреплённый `packageManager`, install-команда и lockfile |
| `Invalid auth settings: BETTER_AUTH_URL, BETTER_AUTH_SECRET, SMTP_HOST, SMTP_PORT, SMTP_FROM` | Эти значения отсутствуют или не проходят проверку в текущем деплое. Проверьте проект, точные имена, область Production и выполните новый Production Redeploy после сохранения. В поле Value вводится только значение, без `KEY=` и внешних кавычек; `BETTER_AUTH_URL` содержит `https://`, секрет — минимум 32 символа, `SMTP_PORT` — число, `SMTP_FROM` — только email |
| Ошибка `DATABASE_URL` / `DIRECT_URL` | Нужное окружение, наличие обоих URL в `.env.vercel`, direct hostname без `-pooler` |
| TLS / ошибка сертификата | Полная строка Neon и действующий endpoint; не отключайте проверку сертификатов |
| `/api/health` возвращает 503 | Доступность Neon, миграции и четыре записи садов; затем `deploy:check` |
| Регистрация выдаёт 403 | Точное совпадение домена с `BETTER_AUTH_URL`, использование постоянного HTTPS-адреса |
| Нет письма | Resend Verified domain, `SMTP_FROM`, API key с правом отправки, квота, журнал отправок и папка «Спам» |
| Письмо приходит только владельцу Resend | Используется `onboarding@resend.dev`; для других адресов нужен собственный подтверждённый домен |
| Локальные изменения не видны на Vercel | Импорт GitHub собирает выбранный коммит из репозитория; Redeploy не загружает локальные файлы |
| SMTP-проверка проходит, письмо не доставлено | `verify()` не отправляет письмо; проверьте отправителя, журнал Resend и реальную регистрацию |
| Авторизация выдаёт 429 | Достигнут общий лимит; дождитесь `X-Retry-After`, проверьте трафик вместо отключения защиты |
| Первый запрос после простоя медленнее | Возможен запуск вычислений Neon/Vercel после простоя; оценивайте и повторный запрос |

Счётчики ограничений теперь общие в PostgreSQL. IP берётся из заголовков ingress только при `VERCEL=1`; вне Vercel используется адрес соединения. Клиентский `x-auth-client-ip` всегда удаляется и формируется сервером заново.

Переменные из локального `.env.vercel` автоматически в Vercel не переносятся. Если после изменения настроек ошибка осталась, проверьте время создания нового деплоя, его окружение и назначение постоянного домена именно ему. Для диагностики достаточно списка имён переменных с областями окружения и свежего текста ошибки; значения секретов раскрывать не нужно.

## Проверки в репозитории

```powershell
corepack pnpm test:unit
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm build
corepack pnpm test:e2e
corepack pnpm test:vercel
corepack pnpm build:vercel
```

`test:vercel` проверяет URL-подключение и Vercel IP-режим на отдельном локальном сервере/временной базе, в том числе параллельные запросы к общему лимиту. Это симуляция окружения, а не проверка настоящего аккаунта Vercel, Neon или Resend. Для браузерных тестов нужны локальные PostgreSQL и Mailpit. Облачные секреты тесты не используют. Сборку и typecheck выполняйте последовательно.
