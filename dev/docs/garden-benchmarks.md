# Воспроизводимые замеры садов

Бенчмарк запускает production-сборку Nuxt в Chromium и сохраняет JSON с диагностикой. Он нужен для сравнения изменений на одном устройстве; автоматических порогов «хорошо/плохо» нет.

## Запуск

Требуются Node.js 24, установленный по lockfile pnpm и Chromium Playwright:

```powershell
corepack pnpm install --frozen-lockfile
corepack pnpm exec playwright install chromium
corepack pnpm build
corepack pnpm exec playwright test --config=playwright.benchmark.config.ts
```

Полный прогон занимает примерно 16 минут. Во время него не запускайте другие сборки, браузерные тесты и тяжёлые приложения. Используйте одинаковые питание, режим производительности и настройки машины для сравниваемых версий.

Конфигурация самостоятельно поднимает `.output/server/index.mjs` на `127.0.0.1:4175` с `NUXT_PUBLIC_GARDEN_DIAGNOSTICS=true`. Порт должен быть свободен; его также использует конфигурация проверки Vercel. Основной `playwright.config.ts`, `.env` и подготовка тестовой базы не подключаются. PostgreSQL, Docker, Neon и почтовый сервер для этих замеров не нужны. Запросы браузера к местам памяти возвращают пустой набор сохранённых записей, авторизация — гостевое состояние. Неизвестный бизнес-API-запрос завершает прогон ошибкой; локальные SVG из `/api/_nuxt_icon/**` загружаются обычным способом. Встроенные демонстрационные места остаются на карте.

Изолированный helper сначала открывает публичный лендинг и ждёт завершения hydration, затем вызывает обычный клиентский `$router.push('/gardens?...')`. Благодаря этому настоящие клиентские middleware получают гостевой ответ через browser mock. Серверная авторизация при этом может оставаться недоступной в штатном режиме лендинга: бенчмарк не перехватывает серверные внутренние запросы и не добавляет исключений в production-код. Доступ к корневому Vue-контейнеру находится только внутри тестового helper, а версии Vue/Nuxt закреплены lockfile и записываются в отчёте. Это проверка первого клиентского входа в сады, а не SSR deep link при работающей базе.

Обычный лимит анимации — 30 тиков/с. Для отдельного сравнения 60:

```powershell
$env:GARDEN_BENCH_FPS = '60'
corepack pnpm exec playwright test --config=playwright.benchmark.config.ts
Remove-Item Env:GARDEN_BENCH_FPS
```

Это настройка диагностического прогона, она не меняет обычное поведение приложения. Первые открытия получают выбранный лимит через разрешённый диагностический параметр `diagnosticsFps`; последующие измерения — через API диагностики. Фактический лимит также записывается в каждом отчёте.

## Фиксированные условия

- Один Chromium, один worker, без повторных попыток; viewport 1440×1000, DPR 1, английский интерфейс, `reducedMotion=no-preference`.
- Seed 424242 задаётся cookie `petmemoreal_garden_session` до открытия страницы и повторяется при настройке измерений.
- Режим диагностики `collect`: панель и её периодические обновления не участвуют в измерении. Запись отдельно включается `beginRun`; переключение режима само не начинает измерение. Скриншоты, видео и trace отключены, дополнительные canvas не создаются.
- Сначала четыре первых клиентских входа в сады из публичной оболочки, каждый в отдельном чистом browser context. Разрешённые параметры `diagnosticsMode=collect&diagnosticsAutoStart=1` начинают запись до создания первого Pixi renderer. Начальный отчёт сохраняется без сброса: учитываются ожидание данных, генерация и первый готовый кадр. SSR/сеть публичной оболочки остаются за пределами коллектора. Это чистый контекст браузера, а не гарантированно холодный GPU/ОС-кеш.
- Затем каждый сад проходит четыре сценария по три повтора: `steady-effects-on`, `steady-effects-off`, `camera`, `pointer-wheel`. Перед каждым повтором — 3 секунды прогрева без записи, затем `beginRun` и 15 секунд измерения.
- Последняя серия — 10 циклов по четырём садам, всего 40 переходов. После каждого сохраняются ресурсы, размеры renderer и счётчик перестроений.

Начальная статическая камера — `zoom=1,x=0,y=0`. В сценарии `camera` она непрерывно следует общей функции `cameraAt`: масштаб плавно меняется между 1.2 и 1.8, а смещение нормализуется по размерам проекции. Движение выполняет существующий Pixi ticker; отдельного RAF, таймера движения или четырёх разовых скачков нет. Во время этого и статических измерений драйвер не читает DOM, не выполняет polling и не делает скриншотов.

Сценарий `pointer-wheel` измеряется отдельно: Playwright отправляет настоящий ввод мыши по общей функции `pointerAt` с частотой до 30 точек/с и восемь событий колеса по фиксированному расписанию. Координаты вычисляются по фактически прошедшему времени. При медленном ответе браузера пропущенные позиции не догоняются: опыт заканчивается через 15 секунд, без очереди из 450 обязательных команд. Уже отправленная команда может завершиться чуть позже границы; после неё новые команды не отправляются. `inputDispatch` сохраняет число отправленных движений/событий и длительность драйвера, а `expected.interactions` — реально обработанный ввод. Если до границы не обработаны все восемь событий колеса или достаточно движений, отчёт признаётся некорректным. Накладные расходы драйвера входят только в этот сценарий. Встроенный браузерный runner использует тот же протокол через синтетические события; происхождение ввода явно отмечается как `synthetic-events`, у внешнего бенчмарка — `trusted-playwright`. Обычные ограничения камеры приложения сохраняются в обоих случаях.

## Отчёты и сравнение

Результаты находятся в `dev/benchmarks/results/<дата>-fps<лимит>-<id>/`: 53 полных отчёта (4 открытия, 48 steady, 1 серия переходов) и `summary.json`. При сбое сохраняется доступная часть с `completed=false`. Каталог конкретного прогона выводится в консоль. Результаты игнорируются Git и находятся вне временного `test-results`, поэтому обычная очистка Playwright не удаляет baseline. Каждый запуск создаёт новый каталог.

У каждого JSON есть `validity: { valid, reasons }`. Проверяются фактические сад, seed, лимит, погода, работающая анимация, режим `collect`, завершённая запись, полная и активная длительность окна не менее 14.9 секунды и наличие выборок. Проверяются как неизменяемые настройки записи, так и фактический `observedContext` на завершении: отключившийся шейдер не может считаться работающей погодой. Для `camera` дополнительно требуется несколько реально изменившихся положений; для ввода — обработанные движения и колесо. Steady-прогон с новой генерацией сцены признаётся некорректным. Это проверка условий опыта, а не требование достичь конкретного FPS или CPU-бюджета. Некорректный отчёт сохраняется, исключается из агрегированных метрик, после записи сводки тест завершается ошибкой.

Каждый JSON содержит параметры сценария, исходный отчёт коллектора и ограниченные сырые выборки. Сводка группирует повторы, показывает интервалы тиков, CPU обновления/отрисовки, частоту реальных рендеров, подготовку сцены и историю ресурсов. Прогрев исключён из steady-измерений: ожидание API и генерация заканчиваются до `beginRun`, поэтому в steady-отчётах ожидаются нулевые счётчики подготовки/готовности и пустые соответствующие выборки. Перестроения считаются с начала конкретного прогона, без вычитания предыдущего прогрева. Первые открытия и серия переходов, наоборот, включают подготовку. В сводке записаны версии Node/Nuxt/Vue/Pixi/Playwright, hash lockfile, Git commit/наличие изменений, CPU/ОС, браузер и доступные сведения о WebGL backend.

Сравнивайте одноимённые группы при одинаковых условиях и версии протокола. Схема 2 с непрерывной камерой требует нового baseline: старые измерения четырёх скачков камеры имеют другую нагрузку. Общие средние взвешены по полному числу измерений; объединённые p50/p95/p99 рассчитываются по сохранённым ограниченным выборкам. CPU-время рендера означает подготовку/отправку команд JavaScript, а не завершение работы GPU. Число объектов и render textures не равно объёму видеопамяти. Результаты headless Chromium со SwiftShader нельзя напрямую считать показателями телефона или браузера с другим GPU.
